## Procedure Calls
```C
void lower(char *s) { 
	size_t i; 
	for (i = 0; i < strlen(s); i++) 
		if (s[i] >= 'A' && s[i] <= 'Z') 
			s[i] -= ('A' - 'a'); 
}
```
![[Pasted image 20260613184433.png]]
换为goto的形式：
```C
void lower(char *s) { 
	size_t i = 0; 
	if (i >= strlen(s)) 
		goto done; 
 loop: 
	if (s[i] >= 'A' && s[i] <= 'Z') 
		s[i] -= ('A' - 'a'); 
	i++; 
	if (i < strlen(s)) //this!
		goto loop; 
 done: 
} 
```
主要的原因是：`strlen(s)`的时间复杂度是$O(n)$，然后for循环$n$次，然后每次循环都会调用这个复杂度为$O(n)$的函数，所以总的就是$O(n^2)$平方时间

所以我们提前`int n=strlen(s)`就可以了
![[Pasted image 20260613185455.png]]

有几个原因使得编译器无法优化：
1. 字符串在循环中被修改了，编译器没理由觉得strlen不会变
2. 由于可能有多个版本的strlen，编译器不知道其是否有[[10-optimization#函数调用|副作用]]（不能假设没有副作用）
## Memory Matters
```C
/* Sum rows is of n X n matrix a and store in vector b */ 
void sum_rows1(double *a, double *b, long n) { 
	long i, j; 
	for (i = 0; i < n; i++) { 
		b[i] = 0; 
		for (j = 0; j < n; j++) 
			b[i] += a[i*n + j]; 
	} 
}
```

## 利用并行性
简单的程序变换可以带来显著的性能提升，编译器通常无法自动完成这些变换，原因之一是：浮点数运算中不满足严格的结合律和分配律。
### CPE
这里我们使用**CPU的时钟周期**来度规时间，Cycles Per Element(CPE)
![[Pasted image 20260613194040.png|659]]
Overhead就是固定开销，比如size=0的情况；Slope就是CPE，表示处理一个元素平均需要多少个 CPU 时钟周期
### Modern CPU Design
![[Pasted image 20260613200016.png|615]]
CPU尽可能多地读取指令序列，然后CPU把读入的指令拆开，发现有的指令不是相互依赖的，CPU就可以直接执行后面的语句（由于指令的独立性）——**指令级并行性**
总结：把程序的操作拆分然后重组，使得基本单元都在工作
> [!NOTE] ICU & EU
> 指令控制单元(ICU)在内存中读出指令序列，并根据其生成一组针对程序数据的基本操作
> 执行单元(EU)会执行这些操作
#### Supersclar Processor
**超标量指令处理器**：在一个时钟周期，可以同时进行多项操作的CPU
#### Pipelined Functional Units
现代CPU采用**乱序执行**，其中功能单元使用了**流水线技术**——将计算分解为一系列不同的阶段
```C
long mult_eg(long a, long b, long c) { 
	long p1 = a*b; 
	long p2 = a*c; 
	long p3 = p1 * p2; 
	return p3; 
}
```
这张表就是流水线技术的体现（表示了一个乘法功能单元内部被分成 3 个 stage），表往下是计算的阶段（流水线拆的——计算乘法要三个步骤），往右是计算的时间（或者说步骤）
![[Pasted image 20260613201340.png|531]]
```
第 1 个 cycle：
a*b 进入乘法器的 Stage 1

第 2 个 cycle：
a*b 被推进到 Stage 2
a*c 同时进入 Stage 1

第 3 个 cycle：
a*b 被推进到 Stage 3
a*c 被推进到 Stage 2

第 4 个 cycle：
a*b 完成
a*c 被推进到 Stage 3

第 5 个 cycle：
a*c 完成
p1*p2 才能进入 Stage 1 (p3依赖于p1,p2，必须等他们做完了才能继续算)
```
#### Haswell CPU
![[Pasted image 20260613203100.png]]
每个指令有两个参数：
- Latency：是一个指令从头到尾执行的时间
- Cycles/Issue：同一个功能单元多久可以接收一条新的同类指令，即**连续两条指令进入流水线的最小时间间隔**
可以看到，除法几乎是没有流水线技术优化的，这是非常昂贵的操作。

##### Loop Unrolling
 ![[Pasted image 20260614162308.png|500]]
这里一次性取出两个元素进行乘法，这样可以**保证可以使用流水线技术**。但是实际上对于乘法来说并没有加速（对加法加速了）。只需略微改动为`x = x OP (d[i] OP d[i+1]);`，就会得到一个两倍加速的程序：
![[Pasted image 20260614184738.png|378]]
区别在于依赖关系变了：
```
x = (x OP d[i]) OP d[i+1]; => (?) OP d[i+1]   ······ (a)
x = x OP (d[i] OP d[i+1]); =>  x  OP   (?)    ······ (b)
```
注意一个非常重要的一点——**CPU不需要等待`i`的递增来访问`d[i]`，他可以直接查询到整个数组里的内容**，而`(b)`式中的`?`是CPU可以提前访问的数组全部内容的相邻乘积——这达成了我们之前的目的：
 ![[Pasted image 20260614183740.png|299]]
 CPU的可能的实际调度是这样的：
 ```
先算 t0 = d0*d1
先算 t1 = d2*d3
先算 t2 = d4*d5

然后按顺序更新 x：
x = x*t0
x = x*t1
x = x*t2
 ```
###### 补充
`x = (((((1 * d0) * d1) * d2) * d3) ...)`：我们只看一个括号内的东西——每个乘法都是形如`? * di`的形式，这就导致了每个乘法都要依赖`?`的结果才能继续算下去。
`x = (((1 * (d0*d1)) * (d2*d3)) * (d4*d5)) * (d6*d7);`：这里直接暴露了所有的独立乘法，括号里面的数都**不是算出来而是取出来的**，他们可以进流水线

## 一些限制因素
本节来源于《CS: APP》
### 寄存器溢出
当我们的并行度超过了可用的寄存器数量，那么编译器就会诉诸*溢出*，将某些临时值放入**内存**中（一般为运行时栈）
![[Pasted image 20260710094733.png|640]]
x86-64处理器有16个寄存器，并可以使用16个YMM寄存器保存浮点数。这里我们会发现20\*20的循环展开反而使得性能降低了
10\*10的内循环：
```
vmulsd (%rdx), %xmm0, %xmm0
```
20\*20的内循环：
```
vmovsd 40(%rsp), %xmm0
vmulsd (%rdx), %xmm0, %xmm0
vmovsd %xmm0, 40(%rsp)
```
从内存读取数据会比较耗时，这会消耗多个寄存器并行的优势
### 分支预测和预测错误处罚
投机执行(speculative execution)：处理器会执行预测出的分支目标处的指令，同时避免修改任何实际的寄存器或内存位置，直到确定了实际的分支结果。
#### 不要过分关心可预测分支
> 现代寄存器的分支预测逻辑非常善于辨别不同的分支指令的有规律的模式和长期的趋势

在之前的例子`combine2`和`combine3`中，我们把边界检查从主循环中拿出来了，也就意味着我们没有在每次循环的时候都检查一遍边界。这大抵是会让性能提高的，但是：
![[Pasted image 20260710104701.png]]
这是由于处理器在此处使用了**条件控制转移**，在绝大部分时候压根没有走越界判断的这个分支（该分支容易预测）
#### 书写适合条件传送实现的代码
对于本质上无法预测的情况（比如判断`x == 1196234`），如果编译器可以产生**条件数据传送**而非条件控制转移的代码，可以极大提高程序性能。此非为C语言程序员可控的，但是有些表达条件行为的方法可以更直接地被翻译为条件数据传送。

## 内存别名使用(memory aliasing)
```C
void p1(int *a, int* b) {
	*a += *b;
	*a += *b;
}

void p2(int *a, int* b) {
	*a += 2* *b;
}
```
以上的两个函数，当`a`和`b`指向同一个地址的时候
`p1`先是`a`自增变为`2a`，然后再是`a=2a+2a=4a`
`p2`直接`a`自增`2a`，变为`3a`
所以，当`a`和`b`指向的不是同一个内存的时候，这两个函数的结果是一样的（后者效率高一些）
这就是**内存别名使用**——编译器必须假设**不同的指针可能指向内存的同一个位置**

另外一个例子
```C
int x = 1, y = 4;
*q = y;
*p = x;
t1 = *q;
```
如果`p`和`q`指向的同一块内存的话，`p`会覆盖掉`q`的值，那么`t1`就是1，反之则是4
## 函数调用
```C
long f();

long func1() {
	return f() + f() + f();
}

long func2() {
	return 3 * f();
}
```
第一个函数会调用3次f函数，而第二个函数只会调用一次（后者更快）。但是编译器并不会把第一个函数优化为第二个函数，这是因为f函数可能有副作用：
```C
long c = 0;
long f() {
	return c++;
}
```

## 分析方法：数据流图
在刚刚看书的时候大概率不会明白数据流图在干嘛，以及为什么要把寄存器分为四种。
寄存器可以分为：
- 只读：循环中不会被修改
- 只写：循环中不会被读取
- **局部**：在循环内部被修改和使用
- **循环**：一次迭代产生的值会在下一次迭代中被用到
样例代码：
![[Pasted image 20260709182739.png|455]]
对应的数据流图：
![[Pasted image 20260709182810.png|181]]
这里我们忽略只读和只写，他们显然绝对不会影响性能：
![[Pasted image 20260709183344.png|187]]
这两个寄存器都是循环寄存器，他们**这一次迭代的值会用到下一次迭代**（注意，这里就会产生所谓的数据依赖，这一次没有算完，下一次就**不会开始计算**）
![[Pasted image 20260709183529.png|186]]
所以这些次循环中会存在一个关键路径，**程序执行必须一关一关地通，没法同时做**（至于为什么关键路径打在mul而不是add上，是因为add可以和mul并行，且前者更快）

我们这里阐述一个事实：**非循环寄存器本身不是性能瓶颈，因为它们通常不会把相邻迭代串起来；CPU 可以通过乱序执行、流水线、投机执行，让这些独立计算提前或重叠进行**
